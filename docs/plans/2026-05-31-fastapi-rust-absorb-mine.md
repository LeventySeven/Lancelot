# FastAPI boilerplate Lancelot should absorb into Rust — fresh mine

## 1. Executive summary

The honest headline of this mine is a near-negative on the Rust front, and that is the load-bearing finding: across six independent angles mining the 24-project FastAPI corpus + AI-startup transcripts, **exactly one candidate scored a clean NEW_RUST_WIN, and it is scope-gated against the positioning lock** (a cross-process model-worker broker — a 30-50h milestone that edges toward "hosting the model"). Two more Rust transforms survive only as **NEEDS_BENCH** (GIL-releasing response compression; SIMD base64 for embeddings) — both have unusually strong corpus evidence (3/24 ship the GIL-bound Python `GZipMiddleware`; vLLM literally vendored `pybase64` with a measured "~3x SIMD" comment), but both are unproven under Lancelot's real load and one only has to beat a `pip install pybase64` users already have. The reason the Rust well is dry is **architectural and already verified in source**: the native `app.run()` server (`src/service.rs:178-285`) collects the body into `Bytes` and passes raw bytes to the handler — it runs **no DI, no body-parsing, no per-route config** (`app.py:877` forwards only `routes`, not even `const_routes`), and `src/stream.rs:40-63` explicitly forbids per-route streaming policy in the Rust pump. So the high-recurrence ingress/streaming/auth boilerplate has **nowhere to plug a zero-GIL Rust path** and must live on the Python ASGI seam — where stdlib hmac/hashlib/zlib are already C-fast. The genuine value this mine surfaces is therefore mostly **Python boilerplate-absorption that does more for the AI-startup dev**: a real **pre-200 streaming-status bug** Lancelot shares with stock Starlette (and that 4 inference servers hand-patch around), a **stuck-stream silence-abort** the keepalive loop actively defeats today (`_send_serialized` bumps the idle timer on its own ping, `asgi.py:978`), an **inbound rate-limiter** (genuinely absent — every `429` in the tree is outbound or the batch shed), a **constant-time API-key gate** (`security.py` only *extracts* credentials, never compares), and a **`response_model` skip-validation** opt-in (benched 4× on a 1000-row read). Net recommendation: ship the Python wins, **bench-gate the two Rust transforms before writing a line**, and do not build the broker until a maintainer makes the positioning call.

## 2. Top NEW wins (ranked)

Ranking weights recurrence × Rust speed/memory leverage × AI-startup relevance × not-shipped × no-bullshit. **Only three candidates have any Rust angle at all; all three are NEEDS_BENCH or scope-gated.** The Python-fine wins (which dominate this mine) are in §3.

### R1 — GIL-releasing response compression (gzip) — **NEEDS_BENCH**
- **Recurring pain:** 3/24 mount Starlette's `GZipMiddleware` on the hot serving path: `dispatch/deep/main.py:59` (`add_middleware(GZipMiddleware, minimum_size=1000)`), `:63`, `:84`; `prefect/deep/api_server.py:476`, `:731`. The DB-backed-web and inference archetypes both return large compressible JSON.
- **The novel axis (why this isn't the old Tier-D rejection):** Starlette's `GZipResponder` runs `gzip.GzipFile(compresslevel=9)` over the whole buffered body **on the event-loop thread, holding the GIL for the entire zlib pass** (verified `.venv/.../starlette/middleware/gzip.py:11`). At level 9 a multi-KB body serializes every *other* request on that worker. The standing Tier-D rejection (CLAUDE.md ~190/208) rejected gzip purely on "the proxy already does it / reimplementing Starlette = useless logic" — it **never reasoned about the GIL cost** of the Python codec. That premise is also **false for single-container PaaS** (the app *is* the edge, no compressing proxy), which M12 made first-class.
- **Proposed surface:** opt-in `App(compress='gzip', compress_min_size=1000)` (or `lancelot.compress.GZipResponder` mirroring Starlette's signature for drop-in swap). On the ASGI seam after serialization: run a Rust `flate2`/`libdeflater` encode under `py.allow_threads`, set `content-encoding` + `vary: accept-encoding`, skip when no `accept-encoding: gzip` / body < min / already encoded / `text/event-stream`. ASGI path only (native `run()` has no body to compress).
- **Rust win mechanism:** GIL release (concurrency — the real prize), single-pass `libdeflate` (~2-3× faster per-byte than Python `zlib`), lower alloc churn (no `BytesIO`+truncate). Speed *and* memory, but the headline is **structural concurrency**, not per-response wall-time.
- **Effort:** 8-12h (3h Rust gzip-under-`allow_threads` + negotiation, 2h seam wiring + stream/CT exclusions, 3-4h the concurrency bench, 1h Tier-D doc revision).
- **Positioning / not-overkill:** squarely byte-path (transport). Opt-in, stdlib-runtime preserved. **Why NEEDS_BENCH:** loopback can't show the bandwidth win — only the GIL-throughput win, which must be measured under concurrent CPU-bound compress (c≈200, level 9) vs Starlette. **And it reopens a documented decision → needs user sign-off before building.**

### R2 — SIMD base64 codec for embeddings / tensors / audio over JSON — **NEEDS_BENCH**
- **Recurring pain:** the inference archetype. `vllm/deep/chat_completion_serving.py:14` `import pybase64 as base64`; `:1086-1087` verbatim comment *"pybase64 is ~3x faster than the stdlib base64 on large payloads thanks to SIMD"*; `:1091-1092` `np.save(buf, ...); base64.b64encode(buf.getvalue())`. `litserve/deep/openai_spec.py:85` `data: str  # base64 encoded audio data`. `ludwig/deep/serve.py:400` `torch.frombuffer(byte_string)`. OpenAI `/v1/embeddings` defaults `encoding_format='base64'`. A production team left a *measured* comment on this exact byte-path cost.
- **Proposed surface:** narrow `lancelot.codec.encode_embeddings(vectors) -> list[str]` matching OpenAI `encoding_format='base64'` (little-endian float32 → SIMD base64, GIL dropped); optional `b64decode(s)` for multimodal input. Framed explicitly as **"the float-array→OpenAI-wire codec,"** not a generic base64 module.
- **Rust win mechanism:** the `base64` crate's SIMD engine (same family `pybase64` binds) encodes a contiguous buffer single-pass under `allow_threads` (GIL dropped) into one pre-sized output buffer. Speed (the ~3× vLLM measured) + modest memory (one output buffer).
- **Effort:** 6-9h (3h Rust SIMD-base64 + float32-LE packing, 1h Python helper, **3-4h the gating bench**).
- **Positioning / not-overkill:** the byte↔wire transform is byte-path (same boundary as `to_json`: the user owns *what* the bytes are, Lancelot owns the wire transform). **Why NEEDS_BENCH (and the bar is high):** the ~3× is vLLM's measurement of `pybase64`, which users get with `pip install pybase64` today. The Lancelot Rust binding must beat **`pybase64`-under-`allow_threads`** materially, not just stdlib. A generic `b64encode` util would be overkill (stdlib is fine for the tiny fixed strings in `security.py:153`/`webhook.py`). **If it only matches pybase64 → document pybase64 and skip.**

### R3 — Multi-worker model broker: per-request-id response demux across a process boundary — **NEW_RUST_WIN (scope-gated; do NOT build speculatively)**
- **Recurring pain:** 4/24 build a cross-process request→response router (the "serving-broker family," `FASTAPI_PRODUCTION_PATTERNS.md:131`). `LITSERVE.md:5`: *"separate OS processes bridged by `multiprocessing.Manager().Queue()` … request tagged with `uid` + `response_queue_id`; handler parks on a per-uid `asyncio.Event`; `response_queue_to_buffer` drains the transport and fires the event"* (`openai_spec.py:514-524`). RayServe (serialize ASGI scope across an actor), Modal (ASGI-over-gRPC). LitServe's `uid`-demux is the cleanest reusable core.
- **Proposed surface (speculative):** `lancelot.broker`: `wq = app.model_broker(channels=N)`; handler does `reply = await wq.submit(payload)` (parks on a Rust `oneshot` keyed by an internal uid) or `async for chunk in wq.stream(payload)` (a Rust `ChunkSink`, **reusing `src/stream.rs`**), with a per-process Rust pump draining a transport and routing by uid.
- **Rust win mechanism (genuine):** the reply router is a hot path — **one demux per streamed token**. A Rust `mpsc`/`oneshot` keyed by request-id routes **GIL-free**, moving `Bytes` instead of pickling, avoiding `multiprocessing.Manager`'s per-item pickle-through-a-proxy-process (LitServe's own documented anti-pattern). Speed (no Manager hop, no per-item GIL) **and** memory (one bounded channel per in-flight uid → backpressure to the worker, vs unbounded Manager queues). This is the **only** item where the bottleneck (per-token routing) and the Rust mechanism (keyed mpsc, zero-copy `Bytes`) genuinely line up.
- **Effort:** 30-50h+ (a new Rust subsystem: per-uid keyed `oneshot`/`mpsc` registry, the process-transport pump, `ChunkSink` reuse for the streaming demux, cross-process backpressure, plus multi-process load + disconnect + worker-death testing). A milestone, not a chunk.
- **Positioning / why NOT now:** routing bytes between processes *is* byte-path, but owning an inbound model-worker broker **edges toward "hosting the model,"** which CLAUDE.md positions firmly as user-side. The technical merit is real (NEW_RUST_WIN); the deploy decision is a **maintainer positioning call**, and it must not precede the cheap, clearly-in-scope §3 wins.

> **Everything else in this mine has no Rust angle.** The two oft-tempting Rust ingress candidates — streaming-multipart parser and zero-buffer reverse-proxy — are both **architecturally blocked** (see §4): the body is already fully resident before any Lancelot code runs (`asgi.py` body-accumulate loop → `requests.py:4` `_BodyAccessor(bytes)`; native path collects to `Bytes` at `service.rs:242`), there is no `request.stream()`, and the native server runs no DI. A Rust scanner has nowhere to stream from. They downgrade to a small Python copy-reduction (NEEDS_BENCH, likely I/O-bound) and a Tier-D-adjacent skip respectively.

## 4. Correctly skipped (ALREADY / TIER_D / AI_LOGIC / NOT_A_BOTTLENECK)

**Architecturally blocked Rust ingress (looked like the biggest wins, aren't):**
- **Streaming/zero-copy multipart parser (Rust) — NEEDS_BENCH→skip.** The triple-copy is real (`uploads.py:111` `.extend(data[start:end])` + `:129` `uf.file.write(bytes(f['data']))`; ZERO multipart in `src/*.rs`). **But:** the native server runs no DI (File()/Form()/UploadFile routes literally don't work on `app.run()`), and on the ASGI path uvicorn fully buffers the body before Lancelot's `receive()` loop runs — `requests.py:4` `_BodyAccessor(bytes)` is resident, there's no `request.stream()`. A Rust incremental parser has **no stream to consume**. The only realizable win is a Python micro-fix (write slices straight into the `SpooledTemporaryFile`), and uploads are I/O-/embedding-bound, so it's likely not the bottleneck. Bench (3-4h) before even the Python fix; the Rust subsystem (40h+, needs a new native ingestion path) is overkill.
- **Zero-buffer reverse-proxy primitive — TIER_D-adjacent skip.** Same blocker (no `request.stream()`, body resident on both paths → can't deliver the zero-buffer property), the only Rust angle (header filter) is a **self-documented non-bottleneck** (`service.rs:225-231`: `dict(headers)` ~100ns, "dwarfed by the GIL+handler call ~50µs+"), and the dominant use (BentoML/Ray model-server reverse proxy) brushes the model-gateway Tier-D line. At most a docs recipe over `TransportPool`.

**Tier-D / positioning (do-not-build, recorded so a future agent doesn't re-derive):**
- **OpenAI `chat.completion.chunk` SSE envelope helper — TIER_D.** The transport half ships (`@app.stream(sse=True, done_sentinel='[DONE]')` + pydantic-core direct-to-bytes, `app.py:474` + `stream.py:43-118`). What's left is the fixed **AI wire contract** (`{id, object, choices:[{delta, finish_reason}]}`), which is the documented Tier-D anti-goal "wire-compatible model gateway." litserve/vLLM/Letta each carry their *own* `ChatCompletionChunk` model — the per-project divergence (role-on-first vs finish_reason='tool_calls' vs `system_fingerprint`) **is** the AI-opinion tell. M15 T8 correctly shipped this as a user *recipe*, not a primitive.
- **Adaptive (latency-learning) SLA batcher — feature-yes / Rust-no, NEEDS_BENCH on the Rust claim only.** BentoML's least-squares `duration ≈ a·n + b` hold-or-shed is a genuine unbuilt primitive and a fair Python feature on top of the existing `_BatchGroup`. But the lstsq + hold-decision run once per *batch* (low frequency) — **not a hot loop**, so a Rust port buys nothing; the existing `@app.batch` bench (~12× / ~16× fewer calls) shows the path is upstream-latency-dominated. If pursued, ship `adaptive=True` in **Python** (hand-rolled 2-var lstsq, no numpy — pydantic-only rule). 10-16h. Not a Rust win.
- **JWT decode + multi-scheme auth factory — Python-yes / Rust-no.** PyJWT is the dominant corpus auth primitive (27 files / 8 projects) and there's no JWT in Lancelot — but HS256 = HMAC-SHA256 over ~200B + `json.loads` of a tiny dict; CPython's `hmac`/`hashlib` are C and there is **no corpus signal it's ever a bottleneck**. The real design tension is the runtime dep (HS256 on stdlib in core; RS256/JWKS behind a lazy optional `cryptography`), not perf. Multi-scheme factory (kill the `makefun` "blood magic" two teams distrust — `authentication_authenticator_FULL.py:7`, polar `dependencies.py:7`) is pure DX, no Rust. Ship in Python if at all; rank below P3/P5.
- **Filter→SQL DSL — AI_LOGIC / boundary violation.** dispatch's `Operator.OPERATORS` produce SQLAlchemy expressions — that's user-side query-building (positioning lock + Tier-D "Lancelot owns transport. Period."). The byte-path sliver (parse + depth-bound untrusted filter JSON) **already ships** (`_json_guard.py:21` + pydantic-core `from_json`). Door closed.

**ALREADY shipped (do not re-derive — M15 + prior):**
- **dict→JSON double-encode** — `validation.py` `_wire_json` is already a single pass (orjson fast path → pydantic-core), so `return {...}`/`return model` never double-encodes (the shipped large-payload win). Stdlib `_json.dumps` fires only if a dev *explicitly* constructs `JSONResponse(content=dict)`.
- **`response_model` double-traversal as a Rust target** — both `validate_python` + `dump_json` already execute in pydantic-core Rust; adapter cached at registration. Collapsing them = reimplementing Pydantic = Tier-D. (The *Python* skip-validation opt-in P4 is the legitimate adjacent win.)
- **Per-param query/header coercion as a Rust target** — pydantic-core Rust; a scalar fast-path risks diverging from the byte-identical 422 envelope, which **is** the conformance floor (974/978, a cardinal gate). Not worth it.
- **CORS, error envelopes (`ProblemDetail`/`retry_taxonomy`), SSE anti-buffering headers, client-disconnect cancellation (C2/M15 unary+stream), TTFT + route-TEMPLATE labels, mid-stream `event:error` frame, traceparent/request-id ingestion** — all verified shipped; the loudest transcript signals are mature.

**NOT_A_BOTTLENECK:**
- **Prometheus `/metrics` text endpoint — TIER_D.** `metrics.py:47` returns OTel **instrument handles only** (`create_counter`/`create_histogram`), retains **zero readable counter state** (verified) — so "render from our own state" silently requires a whole parallel metric store that would drift from the OTel numbers. The OTel→Prometheus exporter exposes these exact instruments at `/metrics` with **zero new Lancelot code**. Document the exporter, build nothing.
- **Streaming cadence/jitter metric** — genuinely NEW and transcript-#1-ranked (`DEEPLEARNINGAI:10379` *"variance is more disruptive than a predictably slower response"*), and Lancelot emits only 2 of the {TTFT, cadence-p99, rate} triad. But it's a monotonic-diff + counter on a loop **already** timing-instrumented for TTFT — **NOT a Rust case** (native pump emits no metrics by design). This is actually a fine ~10-line Python observability add (folds into P2/P6 work); listed here only to flag the Rust angle is nil.
- **Pagination/list-response as a *perf* play** — the cost is the DB `COUNT(*)` + offset/limit (user-side SQL); parsing ints is nanoseconds. P9 is justified as **boilerplate-absorption + a DoS-cap resilience** win, never as Rust/perf.

## 5. Validate-under-load gate (cardinal rule #2: green unit tests ≠ works under load)

Nothing below ships before a **real-server subprocess + HTTP** measurement; loopback unit tests cannot prove any of these.

1. **R1 (gzip) — the gate IS the decision.** Bench a CPU-bound compress at c≈200, level 9, **Rust-`libdeflate`-under-`allow_threads` vs Starlette `GZipMiddleware`**, measuring per-worker *throughput under concurrency* (the GIL cliff), not single-response wall-time. Loopback can't show the bandwidth win, so the bench must isolate the GIL-serialization. **Also requires user sign-off** (reopens the Tier-D gzip rejection). No bench + no sign-off → no build.
2. **R2 (SIMD base64) — high bar.** Bench at representative embedding sizes vs **BOTH stdlib base64 AND `pybase64`-under-`allow_threads`**. Must beat `pybase64` *materially* (users already have it via pip). If it only matches → recommend "document pybase64," do not add a Rust dep.
3. **R3 (broker)** — gated first on a **maintainer positioning decision**, then on real multi-process load + disconnect + worker-death tests (the per-token routing + cross-process backpressure are exactly where a TestClient hides bugs).
4. **Multipart Python micro-fix** — bench N concurrent (c≈50) 10-100 MB uploads, attribute RSS + p99 between the parser memcpy and disk I/O + downstream embedding **before** touching `uploads.py`. Likely I/O-bound → likely skip.
5. **All resilience/streaming Python wins (P1, P2, P6, P8)** — each must be validated on the path the bug lives on: P1 a handler that **raises before its first yield** (assert a real 4xx, not a half-open 200); P2 a generator that **emits only pings** (assert the connection drops at `max_stream_silence` and the gen's `finally` ran); P6 a **mid-stream raise AND a client disconnect** (assert `error-frame` + terminal `[DONE]` on both, across TestClient *and* a native subprocess); P8 a **client that disconnects mid-relay** (assert the upstream stream is actually cancelled). P3 the rate-limiter under a **flood** (assert 429 + `Retry-After` and that the per-process caveat is documented).

**No speed claim in §2-§3 is to be stated as fact until measured on a real server.** The only proven numbers carried in are the existing envelope (const tier 183k, large-payload ~2.3×@69KB, batch ~12×) and the P4 micro-bench (4× on a 1000-row read, pydantic-core, already-Rust).
